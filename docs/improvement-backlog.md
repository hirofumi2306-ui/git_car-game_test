# 改善バックログ「頑張ろうニッポン！」— 不具合・改善点・新機能アイデア総覧

- 作成: 2026-11-28（Muse 総点検＋独立レビュー統合版）
- 対象: 公開版 index.html（v7/v8 反映後）＋ Supabase フェーズA/B1/B2
- 構成: 優先サマリー → 1. 不具合・問題点（13件）→ 2. 改善点（10件）→ 3. 新機能アイデア（20案）
  → 4. 設計済みだが未実装の宿題 → 5. プレイテスト結果（追記予定）

## 優先サマリー（まず直したい順）

1. **ガチャ結果サマリーに「かけら 0 / 万能かけら 0」が常時表示される**（1-1）— 存在しない資源の0表示。体感に直結する確定バグ。
2. **デイリーの文言「全員が同じ敵の並び」と実装の乖離候補**（1-8）— 敵生成が Math.random 依存で日付シードが見当たらない。公平性の約束に関わる。
3. **ドロップのシード同期の綻び**（1-5 / 1-6）— シード取得失敗時は演出ゼロでもサーバーが付与して結果画面で突然増える／サーバー期限30分を過ぎたランでは表示と確定数がずれる。
4. **天井表示のオフバイワン候補**（1-10）— 端末 GACHA_PITY=40 に対しサーバー条件は pity>=39。
5. **ガチャ冪等リプレイ時に何が出たか分からない**（1-9）— duplicated 経路が outcome/coins を返さない。

改善の目玉: BGM 2曲で約10.7MB（再エンコードで大幅削減可）、shadowBlur 31箇所と毎フレームのグラデーション生成（スマホ性能）、ドロップ日次残量（60個上限）の可視化、スコアキャップ到達の明示。

新機能の目玉（第3節より）: 協力レイド（全員の合算で週ボスを削る）、全員同一シードの週替わりチャレンジ、1発勝負「一撃チャレンジ」、メーカー熟練度、結果シェア画像。

## 1. 不具合・問題点

### 1-1. ガチャ結果サマリーに「かけら／万能かけら」が常時0で表示され続ける
- 根拠: 結果サマリー描画は `sh=g.cards.filter(c=>c.out==='shard').length`、`un=g.cards.filter(c=>c.key==='universal').length` を数えて `'NEW '+nw+' / かけら '+sh+' / 万能かけら '+un` を描く。一方フェーズB2のサーバー（`docs/supabase/phase-b2-economy-update.sql` の `gacha_pull`）が返す `outcome` は `new` / `coins` の2種のみ（B1では `shard` / `universal` もあった）。
- 内容: 10連を引くたびに「かけら 0 / 万能かけら 0」という、もう存在しない資源の集計が表示される。プレイヤーには「かけらが貯まっていない＝損した」ように見える。

### 1-2. `outcome='shard' / 'universal'` を処理する死に分岐が結果表示の各所に残存
- 根拠: `gOutTxt`（`c.out==='shard'?'かけら+1'`、`'万能かけら+1'`）、`gOutLong`（`'所持済み → かけら×1 に変換'`、`'万能かけら×1(どの会社にも使える)'`）、`gName` の `universal` 分岐。
- 内容: B2サーバーはこれらを二度と返さないため到達不能。ただし履歴表示の `company_key==='universal'?'万能かけら'` はB2以前の `gacha_log` レコード表示として正しいので、消すなら「新規結果の分岐」と「履歴の分岐」を分けて考える必要がある。一括置換で履歴まで壊すリスクがある箇所。

### 1-3. コメントが実装と正反対の内容を述べている
- 根拠: `NLV_COIN` 定義直前のコメントは前半で「かけらはサーバーで消費: 会社かけら→万能かけら。コインは成功時のみ端末で差し引く（H4）」と述べ、直後に「レベルアップはコインのみ(phase-b2)」と続く二重コメントになっている。`NCO` 定義部のコメントも「所持・レベル・かけらはサーバー(supplier_state)が正」のまま。
- 内容: 次に触る人（Claude Code含む）が前半だけ読むと、廃止済みのかけら消費を復活させる事故が起こり得る。

### 1-4. 使われなくなった `gst.sh` / `gst.univ` を今も localStorage に保存・復元している
- 根拠: `supStLoad` は `supplier_state` の応答から `gst.sh`（会社別かけら数）と `gst.univ`（万能かけら）を構築し、`gstSave()` が `SUPST_KEY='lgsupst'` に `{lv, sh, univ, aid}` を保存する。B2以降レベルアップはこれらを一切参照しない（`nsLevelUp` / `nsLvPanel` は `NLV_COIN` と `coin_cost` のみ）。
- 内容: 実害は小さいが、アカウント切替時の古い状態混入の温床。サーバー側 `supplier_shards.shards` 列と `ruby_wallets.universal_shards` 列も同様に「残っているが使われない」状態で、将来の自分が「まだ生きている資源」と誤認しやすい。

### 1-5. シード取得に失敗すると「見えなかったルビー」が結果画面で突然増える
- 根拠: `rdStart()` は `start_run_seed` の取得失敗を `catch(e){}` で握りつぶし、その場合ラン中はドロップ演出が一切出ない（`rdStep` は `r.seed==null` で即return）。一方サーバーB2の `submit_run` はシード無効時に従来の `random()` 抽選へフォールバックしてルビーを付与する。
- 内容: プレイ中0個表示 → 結果画面で「ルビー +3」と出る、という説明不能な増え方が起きる。逆に、シード取得が遅れてラン開始直後の撃破に間に合わないケースは `while(r0.rdK<r0.kills)rdStep(r0,null)` で巻き取り処理があるが、巻き取り分は演出なしでカウンタだけ増える（`rdStep(r0,null)` は敵座標なしで呼ばれる）。

### 1-6. シードの有効期限（サーバー30分）と端末表示がずれる経路がある
- 根拠: B2 SQLの `submit_run` はシード条件として `used_at is null` かつ `created_at > now() - interval '30 minutes'` を要求する。端末側には期限の概念がなく、ポーズしたまま30分放置したランでも表示カウンタはシード抽選のまま進む。
- 内容: その場合サーバーは期限切れとして `random()` 抽選に切り替えるため、表示ドロップ数と確定数が一致しなくなる。「表示と確定数を一致させる」というI3の設計目的そのものが崩れる経路。ラン自体は短いので頻度は低いが、ポーズ放置はスマホでは普通に起こる。

### 1-7. シードが「プレイ前に確定・端末に開示」されるため、ドロップ位置を事前計算できる
- 根拠: `start_run_seed` はラン開始前にシードを返し、抽選は公開アルゴリズム `xs32`（端末・サーバー共通、v8指示書に明記）。撃破数に対するドロップ発生位置は開始時点で全て計算可能。
- 内容: 友人間ゲームなので実害は小さいが、「サーバー乱数で改ざん不能」という当初設計（フェーズA）からは後退している。シードを何度も取り直す行為（開始→即終了の繰り返し）への歯止めも、サーバー側は「最新1件のみ有効」の上書きのみで、発行回数の制限はない。

### 1-8. デイリーのUI文言「全員が同じ敵の並び」と実装が一致していない疑い
- 根拠: ランキング画面のデイリー説明は「全員が同じ敵の並び・1日3回・ベストが順位に載ります」。しかし敵生成 `spawn()` / `mk()` は `Math.random()` 依存で、デイリー専用のシード付き乱数はコード内に見つからない（シードがあるのはルビードロップの `xs32` のみ）。日替わり修飾子 `DMOD` は日付で全員共通だが、敵の並び自体はプレイヤーごとにランダムに見える。
- 内容: 文言どおりの公平性を担保するなら、デイリーは日付シードでスポーン列を固定すべき。現状は「同じ条件（修飾子）だが並びは各自ランダム」が実態の可能性が高い。

### 1-9. ガチャの冪等リプレイ時に「何が出たか」が結果画面で分からない
- 根拠: B2 `gacha_pull` の重複（`duplicated`）経路は `gacha_log` から `rarity` と `company_key` だけを再構築して返し、`outcome` / `coins` を含まない。端末の `gOutTxt` は該当分岐がなく `'受取済み'` 表示になる。
- 内容: 通信リトライで再送された場合、プレイヤーは自分が何を引いたのか結果画面で確認できず、履歴画面まで見に行く必要がある。二重課金は防げているが「引いた実感」が消える。

### 1-10. 天井表示のオフバイワン候補
- 根拠: 端末は `GACHA_PITY=40` を定数表示に使い、サーバーの天井条件は `v_pity >= 39`（＝39回外れた次の1回が★4以上確定）。端末が「あと (40 - pity) 回」と表示する実装だと、確定回直前で表示が1回ずれる。
- 内容: 確率表示（`GACHA_RATES`）と同様、天井も「サーバーの値をそのまま表示」が原則のはずが、ここだけ端末定数に依存している。

### 1-11. スコア安全キャップの余裕が薄く、頭打ちがプレイヤーに伝わらない
- 根拠: `scoreCap()` は `SCORE_SAFE_KILL=380` / `SCORE_SAFE_STAGE=1950` で、サーバー検証式（`kills*400 + 2000*(stage+1)`）に対して殺し数側5%・ステージ側2.5%の余裕しかない。`scoreClamp()` は毎フレーム呼ばれ、`run.capped=1` を立てるが、その事実を結果画面等で明示する表示は確認できなかった。
- 内容: 上手いプレイヤーほど「スコアが途中から増えなくなった」体験をする。サーバー式が将来変わればキャップ側だけ古くなる二重管理でもある。

## 4. 設計済みだが未実装の宿題（Muse の監査記録より）

以下はレビュー対象のコード外（サーバー設計・プロジェクト管理）の残件。

### 4-1. フェーズC: ルビー報酬の残り（ユーザー設計済み・未実装）
- ランキング報酬 `claim_rank_reward`：日次 1位30 / 2〜3位20 / 4〜10位10ルビー、週次はその2〜3倍。締めは JST 翌04:00 のような確定ルールが必要（順位確定前に受け取れないように）。
- ボス撃破ボーナス：ボス撃破で3〜5ルビー保証。実現には `submit_run` へ `p_boss` 引数の追加と端末側の対応がセットで必要。
- 初回クリア報酬5ルビー、図鑑実績報酬5〜10ルビー。

### 4-2. ライバル表示の実データ未検証
- 「1つ上の順位の人との差」表示はダミーデータでのみ確認済み。実ランキング（6人）で正しく出るか未検証。プレイテストまたは実データ確認が必要。

### 4-3. 既存15社をガチャプールに入れるか未決定
- 現在ガチャは新規12社のみ。既存15社（レベルは端末管理）を混ぜるとサーバー管理への移行が必要になるため保留中。設計判断待ち。

### 4-4. パスワード未設定のプレイヤー行が1件
- `players` に `password_hash` が NULL の行が1件ある（そのアカウントは「パスワード未設定」でログイン不可になるだけで穴ではない）。心当たりがあるかの確認待ち。

### 4-5. 旭化成ロゴの差し替え（任意）
- 元写真の右端がタイトで「I」が際どい。余白のある写真があれば差し替えると綺麗になる。現状でも表示可能。
