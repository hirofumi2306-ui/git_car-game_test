## 1. 認証とSupabase連携

### 1-1. ログイン/登録が遅い主因候補: 直列の多段リクエスト＋タイムアウトなし
- 重大度: 中
- 根拠: `nreq`（index.html 234行）、`ensure`（235行）、`rpc`（236行）、`doAuth`（258〜267行）、`cloudSync`（271〜275行）
- 内容: ログイン1回の処理が全て直列 await でつながっている。(1) `rpc()` が毎回 `ensure()` を先行実行し、セッションが無い/期限切れなら匿名サインアップまたはリフレッシュ（+1往復）、(2) `login` RPC 本体（+1往復）、(3) 成功直後に `cloudSync()` が `load_cloud` RPC（+1往復）、(4) 状態によっては続けて `cloudPush`（+1往復）。合計3〜4往復の直列通信が終わるまで「確認中...」のままになる。`nreq` の fetch には AbortController 等のタイムアウトが一切なく（コード全体で AbortController 使用 0件）、1リクエストが詰まるとUIは無期限に待つ。観測された15〜20秒という遅さは、この直列構造に加え、Supabase側の応答遅延（無料枠のコールドスタート/ポーズ復帰など）やモバイル回線の再送が重なった可能性が高い。ランキング表示でも `fetchBoard`（238行）が `syncTitle` RPC を await してから本体のランキングRPCを呼ぶ直列2段になっており、同種の遅さが出る。
- 修正の方向性: fetch にタイムアウト（例: 8秒で Abort）を入れ、失敗時は再試行導線を出す。`ensure()` の結果をメモ化し、ログインRPCと `load_cloud` の依存関係を見直す（プロフィール取得とセーブ同期の分離）。体感対策として段階的な進捗表示（「接続中→認証中→同期中」）も有効。

### 1-2. パスワードの保存方式がクライアントから確認不能（平文の可能性を否定できない）
- 重大度: 重大（候補）※サーバー側確認が取れるまで「未確認」
- 根拠: `doAuth`（261行）— `rpc('register',{p_nickname, p_pass, p_passcode})` / `rpc('login',{p_nickname, p_pass})`
- 内容: アカウントは Supabase Auth ではなく、Postgres のカスタムRPC（register/login/set_password）で処理され、パスワードはRPC引数として（HTTPS経由で）平文のまま渡される。DB側で pgcrypto（bcrypt）等によりハッシュ化されているかはクライアントコードからは一切判断できない。もし平文または可逆な形で保存されていれば重大な問題になる。エラー種別に `locked`（「失敗が続いたため、10分間ロック」、`ERR` 定義 252行）があり、サーバー側でブルートフォース対策のロックアウトが実装されている形跡がある。
- 修正の方向性: サーバー側（Supabaseダッシュボード/SQL）で register/login 関数が `crypt(p_pass, gen_salt('bf'))` 等でハッシュ化しているかを確認する。平文なら即時移行。可能なら Supabase Auth 本体への移行も検討。

### 1-3. セッション（リフレッシュトークン含む）を localStorage に平文保存
- 重大度: 中
- 根拠: `saveSess`（233行）、`sess` 読み込み（232行）、キー `'lgsess'`
- 内容: access_token と refresh_token を localStorage の `lgsess` に保存している。localStorage は同一オリジンのJSから自由に読めるため、XSSがあれば長期有効な refresh_token ごと奪取される。現状コードは innerHTML 使用 0件・eval/new Function 0件で、UIは canvas 描画と textContent 中心のため、現時点のXSS面は小さい。ただし将来 innerHTML を使う改修が入ると即リスク化する。
- 修正の方向性: 現構成（静的ホスティング＋RPC認証）では Cookie 方式への移行は難しいため、最低限「innerHTML を使わない方針の明文化」と、refresh_token の保存を前提にしたCSP導入を検討。トークン有効期限の短縮もサーバー側設定で確認。

### 1-4. 全通信が publishable key＋匿名ユーザー経由のRPC依存で、安全性はサーバー実装に全面依存
- 重大度: 中
- 根拠: `NET`（230行、`sb_publishable_` キーをクライアント埋め込み）、`submitRun`（241行）、`rpc`（236行）
- 内容: Supabase の publishable key（anon key 相当）がクライアントに埋め込まれていること自体は仕様どおりで、それ単体は問題ではない。ただし読み書きは全てRPC経由で、スコア送信 `submit_run` はスコア・撃破数などをクライアント申告値のまま送っている。RPC側で値の妥当性検証（ありえないスコアの排除など）や、RLS/関数の権限設定が適切かはクライアントから検証できない。検証が無ければランキング改ざんが可能。
- 修正の方向性: サーバー側で各RPCの実装（SECURITY DEFINER の有無、引数検証、呼び出し元チェック）を棚卸しする。スコアは「サーバーで再計算可能な材料（シード等）」を送る方式が理想だが、最低限の上限チェックでも効果がある。

### 1-5. 匿名サインアップの自動実行と弱い端末紐付け
- 重大度: 軽微
- 根拠: `ensure`（235行、`POST /auth/v1/signup` に空データ）、`ERR` の `device_has_account`（252行）
- 内容: セッションが無い状態でRPCが必要になると、自動で匿名ユーザーを作成する（サーバー側で匿名サインインが有効な前提）。未登録の訪問者でも auth ユーザーが作られ続ける。登録時の「この端末は登録済みです」判定は匿名ユーザーの uid 紐付けとみられ、localStorage を消す/別ブラウザにするだけで回避できる弱い binding である可能性が高い。
- 修正の方向性: 匿名ユーザーの発行は必要最小限のタイミングに絞る。端末紐付けは「抑止」程度の位置づけとして明示し、強い本人性が必要なら別手段を検討。

### 1-6. 合言葉（招待コード）の扱い
- 重大度: 軽微（運用上の注意）
- 根拠: `doAuth`（261行、`p_passcode` をRPCへ送信）、39行の入力欄
- 内容: 合言葉そのものはクライアントコードに埋め込まれておらず、照合はサーバー側RPCで行われる。一方で合言葉は全ユーザー共通の単一コードであり、漏洩した場合に無効化・変更する手段はサーバー側の変更のみになる。
- 修正の方向性: 漏洩時のローテーション手順を決めておく。規模が大きくなれば招待コードの個別発行への移行を検討。

### 1-7. 引き継ぎコードの保護が弱い（弱いチェックサムのみ）
- 重大度: 軽微
- 根拠: `hsh`（245行付近、31倍加算の32bitハッシュ）、`mkCode`/`parseCode`（246〜248行付近）
- 内容: 引き継ぎコードはセーブデータ全体を base64 化したもの＋弱いチェックサムのみで、暗号化も署名もない。コードを知る者は内容の閲覧・改ざん（コインやXPの水増し等）が可能で、そのままクラウド同期されるデータにもなりうる。ユーザー自身が管理するコードという設計上の割り切りではあるが、チート耐性はない。
- 修正の方向性: 割り切る場合は仕様として明記。対策するならチェックサムを HMAC 等に変える（ただし鍵をクライアントに置く限り限界はある）。サーバー側で不自然なジャンプ（XP急増など）を検出する方が実効的。
